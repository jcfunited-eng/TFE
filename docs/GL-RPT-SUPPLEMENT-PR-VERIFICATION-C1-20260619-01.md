## 1. pr.atlas size — CANNOT BE INSPECTED REMOTELY

There is no API endpoint, introspection command, or substrate_runner handler that exposes `guala.hemispheres["pr"].atlas`. The pr hemisphere lives as an in-memory `HemisphereCoordinator` attribute on the `_guala` object inside the substrate process. No path from the HTTP API reaches it.

Checked:
- `/status` → does not expose hemisphere state
- `/diag` → returns `{"response": ..., "motifs": ...}` only
- `/api/v1/gualaloom/admin/atlas_snapshot` → returns the global em atlas only
- `guala_atlas_query` → queries the em atlas only
- `/events` → hemisphere_update events show convergent_event counts but not pr.atlas binding counts
- CloudWatch logs → no pr-specific log lines

**This is a gap in the instrumentation.** pr.atlas is not observable from outside the substrate process. A future brief should add a hemisphere introspection endpoint (e.g. `/api/v1/gualaloom/admin/hemisphere_state`) that exposes per-hemisphere atlas binding counts.

## 3. Pre-flip vs post-flip behavioral difference — CONFIRMED

```
$ curl ... /events?n=1000 | ... filter hemisphere_update

hemisphere_update events in last 1000: 2
  tick=11238526 n_events=134020
  tick=11238583 n_events=103229

pre-flip hemisphere_update: 0
post-flip hemisphere_update: 2
```

**Zero `hemisphere_update` events at pre-flip ticks. Two at post-flip ticks.** The event log persists across task restarts on EFS. The 1000-event window covers both task:207 and task:208 lifetimes. `hemisphere_update` events exist ONLY in the post-flip window.

This is because `run_hemisphere_updates()` in `hemisphere_cognition.py` checks `os.environ.get("HEMI_PR_ENABLED", "0") == "1"` before doing any pr work. With the flag at 0 (task:207), the function returns an empty events list and `_log_substrate_event("hemisphere_update", ...)` is never called (it's gated on `if events_log:`).

The convergent_event entries at ticks 11238526 and 11238583 were generated by task:208 (post-flip). Eve's observation that they appeared "while task 207 had HEMI_PR_ENABLED=0" was incorrect — those ticks are from the V3 test inputs sent to task:208 (post-flip). The tick numbers are substrate ticks (continuous across restarts), not task-specific — both tasks share the same tick counter from EFS state.
