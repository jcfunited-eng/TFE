4. Ingestion/DB Guarantees (WHAT PHASE A MUST PROVIDE)
UF Engine contract defines what ingestion must guarantee:
Canonical OHLCV:
For a given (symbol, start_date, end_date, timeframe="1D"), DB must return:
A chronologically ordered series of records:
date, open, high, low, close, volume.
No duplicates:
There must be at most one row per (symbol_id, date, timeframe).
If ingestion duplicates exist, UF Engine must see only one canonical value per date.
Monotonic ordering:
Records must be sorted ascending by date.
UF Engine assumes ascending order; it does NOT resort.
Adjusted close prices:
close must be adjusted for splits and dividends if using adjusted series.
This must be documented and consistent (UF is agnostic but must get a consistent series).
Gap semantics:
For missing trading days (weekends, holidays) → they do not appear in DB; UF knows how to handle gaps.
For unexpected missing days (non-holiday with no bar):
Either:
ingestion fills or flags them, or
UF Engine must receive them as missing and has defined behavior:
It can log a warning, drop those days, or adjust.
Recommendation:DB should simply not store rows for missing days; UF Engine treats absent days as non-trading days.
Data type constraints:
open, high, low, close → finite numeric (not NaN/inf).
volume → >= 0 (numeric).
If any OHLC is invalid for a day, ingestion must not insert that row or mark it invalid; UF Engine assumes valid numbers only.
Time alignment:
For daily bars, all date values represent the same calendar concept (e.g. 00:00 UTC or market session date).
UF Engine does not handle time-zone conversions; ingestion must unify this.
This is what Phase A implementation must enforce.
